Protecting data comes in two states, and the exam expects you to tell them
apart. Data at rest is data sitting in storage, such as a file in Amazon S3 or a
disk volume. Data in transit is data moving across a network, such as a request
travelling from a browser to your application. Encryption protects both: it
scrambles the data so that only a holder of the right key can read it. The
services below give you the keys, the certificates, and the credential storage to
do that across AWS.

## AWS KMS manages your encryption keys

AWS Key Management Service (AWS KMS) is a managed service for creating and
controlling the keys that encrypt your data. The keys you create, called KMS
keys, are protected inside hardware security modules and never leave the service
in plaintext. Most AWS storage services integrate with KMS, so you can turn on
encryption for S3, EBS, RDS, and others, and KMS handles the key for you.

KMS keys come in a few types, and the difference is about who controls them. An
AWS managed key is created and rotated by an AWS service on your behalf; you do
not manage it and there is no monthly charge for the key to exist. A customer
managed key is one you create and fully control: you set its access policy,
enable or disable it, and choose its rotation, and it carries a monthly cost.
Reach for a customer managed key when you need that control; otherwise the
managed option is simpler. A third type, the AWS owned key, sits in an account
the service owns rather than yours, costs nothing, and asks nothing of you, but
you cannot see its policy or audit its use, so a requirement to audit key
activity rules it out.

<Callout type="key" title="Managed versus customer managed">
If a scenario stresses full control over the key, its policy, or its rotation,
the answer is a customer managed key. If it stresses convenience and no key
administration, an AWS managed key fits.
</Callout>

### Encryption at rest across services

Many services encrypt at rest by default, so the real question is usually which
key they use. Amazon S3 applies server-side encryption with Amazon S3 managed
keys (SSE-S3) as the base level of encryption for every bucket, so since
January 5, 2023 new object uploads are encrypted automatically at no additional
cost; if you need to control the key yourself, choose SSE-KMS and point it at a
customer managed key. Amazon DynamoDB encrypts all table data at rest through
its AWS KMS integration, using an AWS owned key unless you choose an AWS managed
or customer managed key.

Amazon EBS encryption happens on the servers that host the EC2 instances, so it
covers both data at rest on the volume and data in transit between the instance
and its attached storage. Snapshots taken from an encrypted volume, and volumes
restored from those snapshots, are encrypted as well, and you cannot encrypt an
existing unencrypted volume in place: you snapshot it and create a new encrypted
volume from that snapshot.

### Envelope encryption, briefly

KMS uses a pattern called envelope encryption, and you only need the shape of it.
Rather than sending all your data to KMS, you ask KMS for a data key. KMS returns
that data key twice: once in plaintext for immediate use, and once encrypted
under your KMS key. You encrypt the actual data locally with the plaintext data
key, then discard it and store the encrypted data key next to the ciphertext. To
read the data later, you send the encrypted data key back to KMS, which decrypts
it so you can decrypt the data. The high-value KMS key stays in KMS and never has
to touch the bulk of your data.

### AWS CloudHSM for single-tenant hardware

Some workloads have to run their cryptography on single-tenant hardware security
modules. AWS CloudHSM provides them: HSMs in the AWS Cloud that no other
customer shares, with full control of the keys and algorithms you use. The data
plane is end-to-end encrypted and not visible to AWS, and the trade for that
control is more operational responsibility than a managed service asks of you.
If you want a managed service for creating and controlling keys and you do not
want to operate your own HSMs, AWS points you at KMS.

## AWS Certificate Manager handles TLS certificates

Encryption in transit on the web means TLS, the protocol behind HTTPS, and TLS
needs a certificate. AWS Certificate Manager (ACM) creates, stores, and renews
the public and private SSL/TLS certificates that secure your sites and
applications. Its main appeal is that it removes the manual renewal work:
certificates ACM issues and that stay attached to an AWS service are renewed for
you, so you avoid an expired certificate taking a site offline.

ACM certificates typically attach to AWS services that terminate TLS for you,
such as Elastic Load Balancing and Amazon CloudFront. Public certificates that
you provision through ACM for use with ACM-integrated services carry no
additional charge; you pay only for the AWS resources running your workload.

## AWS Secrets Manager stores and rotates secrets

Applications need credentials such as database passwords, API keys, and tokens,
and hardcoding them in source code is a common security mistake. AWS Secrets
Manager stores those secrets and hands them to your application at runtime
through a call to the service, so the credential is not baked into the code or
the deployment.

Its standout feature is rotation. Secrets Manager can rotate a secret on a
schedule you configure, replacing a long-lived credential with a fresh one
without you editing and redeploying the application. That shrinks the window in
which a leaked credential is useful. Note the division of labor with KMS: KMS is
for encryption keys, while Secrets Manager is for application credentials, and
Secrets Manager uses KMS underneath to encrypt the secrets it holds.

AWS Systems Manager Parameter Store is the other place AWS stores configuration
data. String and StringList parameters hold plain text, SecureString parameters
are encrypted with AWS KMS, and standard-tier parameters carry no additional
charge. Reach for Parameter Store for configuration values such as endpoint URLs
and environment names, and for Secrets Manager when a credential has to be
rotated automatically.

<Callout type="note" title="KMS or Secrets Manager?">
A question about managing cryptographic keys points to KMS. A question about
storing database or application credentials and rotating them points to Secrets
Manager. They work together, but they answer different needs.
</Callout>

## What to take away

Know the two states of data, at rest and in transit, and that encryption
protects both. KMS manages encryption keys, with customer managed keys for
control and AWS managed keys for convenience, and it uses envelope encryption so
the key stays in the service. ACM issues and auto-renews TLS certificates for
services like load balancers and CloudFront. Secrets Manager stores credentials
out of your code and rotates them on a schedule. Matching each service to its job
is what the exam asks of you here.
